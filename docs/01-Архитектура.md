# Архитектура системы FinFlow

## 1. Общая схема

Система построена как модульный монолит с разделением на слои. Физически это
два клиента (WPF и веб) и один сервер приложений, работающий с SQL Server.

```
┌──────────────────────────┐        ┌───────────────────────────┐
│ WPF: операционный контур │        │ Веб: аналитический контур │
│ операционист, контролёр, │        │ КУАП, казначейство, риск, │
│ бухгалтер, администратор │        │ ПОД/ФТ                    │
└────────────┬─────────────┘        └─────────────┬─────────────┘
             │  HTTPS, Bearer-токен               │
             ▼                                    ▼
┌────────────────────────────────────────────────────────────────┐
│                       FinFlow.Api (ASP.NET Core)               │
│  аутентификация FinFlowToken · авторизация по ролям · Swagger  │
│  контроллеры · ProblemDetails · статические файлы веб-клиента  │
└───────────────────────────────┬────────────────────────────────┘
                                ▼
┌────────────────────────────────────────────────────────────────┐
│                      FinFlow.Application                       │
│  сервисы (Service Layer) · абстракции · маппинг · правила      │
└───────────────────────────────┬────────────────────────────────┘
                                ▼
┌───────────────────────────────┴────────────────────────────────┐
│ FinFlow.Infrastructure                    │  FinFlow.Domain    │
│ EF Core · Unit of Work · хеши паролей     │  сущности, расчёты │
│ токены · шлюзы интеграций · инициализация │  модельные данные  │
└───────────────────────────────────────────┴────────────────────┘
                                ▼
                           SQL Server
```

## 2. Слои и ответственность

### FinFlow.Domain — предметная область

- `Common/` — `BaseEntity` (Id, RowVersion, CreatedAt, CreatedBy, IsDeleted),
  `Money` (округление денег до 2 знаков, ставок — до 6), `DomainException`.
- `Enums/BankEnums.cs` — 22 перечисления: `ClientType`, `IdentificationStatus`,
  `KycRiskLevel`, `DepositType`, `ProductKind`, `AccountStatus`, `NumberKind`,
  `OperationKind`, `OperationStatus`, `DocumentSource`, `ContractStatus`,
  `HoldSource`, `HoldStatus`, `DayCloseStage`, `OperationalDayStatus`, `RiskStatus`,
  `RoleCode`, `RiskZone` и другие, вместе с русскими подписями (`DisplayName()`).
- `Entities/` — 8 файлов сущностей: клиенты и ПОД/ФТ, продукты и версии, счета и
  номера, договоры, операции и документы, проводки, начисления и удержания,
  операционный день, параметры, риски, пользователи и роли, аудит, прогноз
  ликвидности.
- `Calculators/` — чистые функции без зависимостей: `BalanceCalculator`
  (1.1–1.4), `InterestCalculator` (1.5–1.7), `TaxCalculator` (1.8),
  `EarlyReturnCalculator` (1.9–1.10), `LiquidityCalculator` (1.11–1.13),
  `MarginCalculator` (1.14–1.16), `RiskCalculator` (1.17–1.20),
  `WorkflowPolicy` (маршрут контроля), `SchedulePolicy` (календарные правила),
  `AccountNumberGenerator` (номера счетов НБРБ № 123).
- `Reference/ModelBankData.cs` — модельные допущения записки: портфель
  240 000 тыс. р., реестр рисков R-01…R-12, параметры 2026 года, пятидневный
  горизонт ликвидности, анализ чувствительности, перечень ролей.

Домен не ссылается на EF Core, ASP.NET Core и WPF — расчётные классы полностью
покрыты тестами без базы данных.

### FinFlow.Contracts — контракты обмена

DTO запросов и ответов (`LoginRequest/LoginResponse`, `ClientDetailsDto`,
`AccountDetailsDto`, `OperationDto`, `EarlyReturnQuoteDto`, `LiquidityForecastDto`,
`MarginReportDto`, `RiskSummaryDto`, `ReconciliationDto` и др.),
`PagedResult<T>`, `MessageDto`, `MetaDto`. Один проект используют и API, и клиенты,
поэтому контракт не может разойтись между сервером и WPF.

22 сервиса, каждый отвечает за свой агрегат:

| `ProductService` | продукты, версии условий, контроль РВСР |
| `AccountService` | открытие/закрытие счетов, номера, овердрафт |

Абстракции (`Abstractions/`): `IBankDbContext`, `IUnitOfWork`, `IClock`,
`ICurrentUser`, `IAuditWriter`, `ITokenStore`, `IPasswordHasher`,
`IAisIdoGateway`, `ILedgerGateway`, `IMsiGateway`, `IEventPublisher`.
Прикладной слой зависит только от них, поэтому инфраструктура заменяема
(например, шлюзы интеграций на реальные адаптеры).

### FinFlow.Infrastructure

- `Persistence/BankDbContext` — 23 набора сущностей, конфигурация таблиц,
  точности `decimal(18,4)`/`decimal(9,6)`, индексы, `RowVersion` как токен
  конкурентности; `BankDbContextFactory` — для `dotnet ef`.
- `Persistence/UnitOfWork` — транзакция на операцию, `SaveChanges` и фиксация.
- `Persistence/DbSeeder` — идемпотентное начальное заполнение.
- `Security/PasswordHasher` — PBKDF2-HMAC-SHA256, 100 000 итераций, случайная соль.
- `Security/InMemoryTokenStore` — токены доступа на 15 минут (в учебной версии —
  в памяти процесса; для промышленной эксплуатации заменяется на распределённое
  хранилище).
- `Integrations/Gateways` — реализации `IAisIdoGateway`, `ILedgerGateway`,
  `IMsiGateway` с сохранением контрактов обмена.
- `DependencyInjection.AddFinFlow` — регистрация контекста, сервисов, шлюзов;
  `InitializeDatabaseAsync` — создание схемы и заполнение данными.

### FinFlow.Api

Точка входа `Program.cs`: строка подключения, `AddFinFlow`, схема
аутентификации `FinFlowToken`, CORS, JSON с `camelCase` и строковыми
перечислениями, Swagger с Bearer, статические файлы веб-клиента,
`/api/health`. 17 контроллеров, разграничение по ролям через
`[Authorize(Roles = ...)]`, ошибки приводятся к `ProblemDetails`
(`ExceptionMiddleware`). Приём документов АИС ИДО — `[AllowAnonymous]`
с проверкой идемпотентности по `ExternalId`.

### FinFlow.Desktop — WPF, MVVM

`Infrastructure/` — `ApiClient` (токен, JSON, разбор ProblemDetails),
`ObservableObject`, `RelayCommand`/`AsyncRelayCommand`, `ViewModelBase`
с обработкой ошибок, `Session` (пользователь + роли).
`ViewModels/` — `MainViewModel`, `ClientsViewModel`, `AccountViewModel`, `OperationsViewModel`,
`ControlQueueViewModel`, `DayCloseViewModel`, `AdminViewModel`.
`Views/` — шесть экранов операционного контура; `LoginWindow` — вход в систему. Навигация: выбор счёта в списке
клиентов автоматически открывает карточку счёта и подставляет его в экран
операций; вкладки «Очередь контроля» и «Администрирование» видны только
контролёру/администратору.

## 4. Транзакции и конкурентность (требование 24)

- Каждая изменяющая операция выполняется внутри `IUnitOfWork.BeginAsync`:
  изменение остатка и формирование проводок фиксируются вместе.
- `OperationService` сериализует исполнение через статический `SemaphoreSlim`,
  что исключает одновременную проверку остатка двумя каналами до списания.
- Перед списанием выполняется повторная проверка доступного остатка (1.1);
  при изменении данных операция отклоняется с указанием фактических значений.
- `RowVersion` включён как токен оптимистической блокировки; конфликт
  `DbUpdateConcurrencyException` преобразуется в `ConflictException` (HTTP 409)
  с понятным сообщением.

## 5. Состояния операции (таблица 1.11)

```
Черновик ──отправка──► На проверке ──┬─► Одобрена ──► Исполнена ──► Отражена
                                     ├─► На контроле ──подтверждение──► Одобрена
                                     ├─► Приостановлена ──решение ПОД/ФТ──► …
                                     └─► Отказано
Исполненная/Отражённая ──сторно──► Сторнирована (исходная запись неизменяема)
```

Маршрутизация (`WorkflowPolicy.Evaluate`):

- сумма ≤ лимита операциониста (5 000 р.) и нет признаков ПОД/ФТ → автоматическое
  одобрение и исполнение;
- сумма > 5 000 р. → «На контроле», требуется подтверждение другого сотрудника
  (автор не может подтвердить свою операцию — бизнес-правило 12);
- признак ПОД/ФТ (наличная операция ≥ 20 000 р. либо повышенный риск клиента) →
  «Приостановлена» и очередь специалиста ПОД/ФТ.

## 6. Закрытие операционного дня (требование 12)

Этапы `DayCloseStage`: `Started` → `PendingRejected` → `AccrualsDone` →
`PayoutsDone` → `ContractsDone` → `PostingsDone` → `Reconciled` → `Completed`.

1. Неподтверждённые операции отклоняются с указанием причины.
2. По каждому действующему договору начисляются проценты за день; повторное
   начисление на ту же дату исключается проверкой `(ContractId, AccrualDate)` —
   повторный запуск закрытия не создаёт дублей.
3. При наступлении даты выплаты или ежемесячной капитализации проценты
   выплачиваются либо присоединяются к вкладу; удерживается налог.
4. Договоры с истёкшим сроком пролонгируются или закрываются с выплатой.
5. Проводки помечаются как переданные в главную книгу.
6. Выполняется сверка оборотов (`GetTurnoverAsync`), результат фиксируется в
   `ReconciliationDto`; расхождение отражается как ошибка дня.

## 7. Безопасность и аудит

- Пароли — PBKDF2-HMAC-SHA256, 100 000 итераций, соль на пользователя.
- Токен доступа — 15 минут, передаётся в `Authorization: Bearer`.
- Второй фактор обязателен для контролёра и администратора.
- 8 ролей (`RoleCode`): операционист, контролёр, бухгалтер, администратор,
  руководитель, казначей, риск-менеджер, специалист ПОД/ФТ; права проверяются
  на каждом действии API.
- Все изменения пишутся в `AuditLog` (только добавление, хранение ≥ 5 лет);
  аудит недоступен для изменения через API.
- Для промышленной эксплуатации: TLS 1.2+, RPO 5 минут, RTO 1 час,
  доступность 99,9 % (нефункциональные требования записки).

## 8. Производительность

Расчётные классы не обращаются к базе; выборки ограничены `take`,
прогноз ликвидности в режиме `db` ограничен горизонтом 90 дней и группирует
договоры по датам окончания. Целевые показатели записки: 140 пользователей,
20 операций/с, p95 ≤ 2 с, закрытие дня ≤ 30 минут для 110 000 договоров.
