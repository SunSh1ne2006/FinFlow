# Архитектура системы

## 1. Назначение и границы

FinFlow — учебная сетевая система управления вкладами и текущими счетами банка.
Она охватывает операционный контур отделения: клиенты, счета, договоры вкладов,
операции, проценты и налог, закрытие операционного дня, отчётность руководителя
и личный кабинет клиента.

Вне границ разработки и удалены из системы: реестр рисков и количественная оценка
рисков, прогноз ликвидности, маржинальный анализ, ПОД/ФТ-контроль и анкеты,
интеграции с АИС ИДО, МСИ, главной книгой и внешними каналами, продуктовый
конструктор с контролем РВСР.

## 2. Слои и зависимости

```
FinFlow.Api (ASP.NET Core)   FinFlow.Desktop (WPF)
        │                            │
        └──────────► FinFlow.Infrastructure (EF Core, безопасность, инициализация БД)
                                     │
                          FinFlow.Application (сервисы, абстракции, маппинг)
                                     │
                              FinFlow.Domain (сущности, расчёты, правила)
```

`FinFlow.Contracts` содержит DTO и запросы, общие для сервера и клиентов.
Зависимости направлены только внутрь; домен не зависит от EF Core и ASP.NET Core.

## 3. Модули прикладного слоя

| Модуль | Классы | Ответственность |
|--------|--------|-----------------|
| Клиенты | `ClientService` | регистрация, идентификация, поиск, изменение данных |
| Продукты | `ProductService` | справочник вкладов и текущих счетов, версии условий |
| Счета | `AccountService`, `BalanceService`, `HoldService` | открытие и закрытие счёта, номера, доступный остаток, ограничения, овердрафт |
| Договоры | `ContractService` | открытие договора вклада, согласие банка на досрочный возврат, расчёт досрочного возврата, начисления |
| Операции | `OperationService` | проведение операций, проверка остатка, исполнение, сторнирование |
| Проценты | `InterestService`, `TaxService` | ежедневное начисление, капитализация, налог с процентов |
| Закрытие дня | `DayCloseService` | начисления, выплаты, пролонгация и возврат вкладов |
| Отчётность | `StaffReportService`, `StaffWorkCalculator` | показатели работы сотрудников за период |
| Администрирование | `AdminService`, `AuditService` | учётные записи, блокировка, журнал аудита |
| Личный кабинет | `ClientPortalService` | вход клиента, его вклады и условия |

## 4. Модель данных

| Таблица | Назначение |
|---------|-----------|
| `Clients` | клиенты банка (физлицо, юрлицо, ИП), статус идентификации, дата рождения для кабинета |
| `Products`, `ProductVersions` | продукты и версии условий (ставка, срок, капитализация, порядок выплаты, минимальная сумма) |
| `Accounts`, `AccountNumbers`, `Holds` | счета, прежний и изменённый номера, аресты и бронирования |
| `Contracts` | договоры вкладов и текущих счетов, тело вклада, начисленные и выплаченные проценты |
| `Operations` | операции по счёту, снимок B/L/H/D, причина отказа, ссылка на сторно |
| `InterestAccruals`, `TaxWithholdings` | ежедневные начисления и удержанный налог |
| `OperationalDays` | операционные дни, этапы закрытия и итоги |
| `Parameters` | ставка налога, ставка до востребования, ставка рефинансирования с датой действия |
| `Users`, `Roles`, `UserRoles` | сотрудники и их роли |
| `AuditLog` | журнал действий (только вставка) |

Ключевые ограничения: уникальность номера счёта, уникальность пары
(договор, дата начисления), уникальность логина, CHECK-ограничения на суммы и
сроки, оптимистическая блокировка через `RowVersion`.

## 5. Роли и доступ

| Роль (`RoleCode`) | Интерфейс | Права API |
|-------------------|-----------|-----------|
| `Employee` | WPF | клиенты, счета, договоры, операции, закрытие дня, продукты (чтение) |
| `Administrator` | WPF | пользователи и блокировка, журнал аудита |
| `Head` | WPF | отчёт о работе сотрудников (чтение) |
| Клиент банка | веб `/client/` | отдельная схема аутентификации: только свои вклады и условия |

Аутентификация сотрудников — логин и пароль, непрозрачный токен в заголовке
`Authorization: Bearer`, блокировка после пяти неудачных попыток. Клиент входит
по номеру документа и дате рождения; сессия клиента хранится отдельно от сессий
сотрудников.

## 6. Ключевые сценарии

### 6.1. Открытие вклада

1. Сотрудник находит или регистрирует клиента (статус «идентифицирован»).
2. Выбирает продукт и версию условий, вводит сумму.
3. `ContractService` создаёт счёт, два номера счёта и договор, ссылающийся на
   версию условий; первоначальный взнос проводится операцией «взнос наличными».

### 6.2. Операция по счёту

1. `OperationService` проверяет, что счёт открыт, клиент идентифицирован, вид
   операции допустим для ручного проведения.
2. Под блокировкой вычисляется доступный остаток `D = max(0; B + L − H)`.
3. При недостатке средств операция сохраняется со статусом «Отказано» и
   причиной; иначе остаток изменяется, операция исполняется, договор
   корректируется (тело вклада, досрочный возврат) в той же транзакции.

### 6.3. Закрытие операционного дня

`DayCloseService` фиксирует этапы в `OperationalDays`:

1. черновики операций отклоняются;
2. начисляются проценты по действующим договорам (идемпотентно по паре
   «договор, дата»);
3. проценты капитализируются или выплачиваются с удержанием налога;
4. вклады с наступившим сроком пролонгируются или возвращаются;
5. день закрывается, итоги фиксируются, действие попадает в журнал аудита.

Повторный запуск после сбоя продолжает обработку с сохранённого этапа и не
создаёт повторных начислений.

### 6.4. Отчёт руководителя

`StaffReportService` выбирает сотрудников с ролью `Employee` и агрегирует за
период: зарегистрированные клиенты, открытые счета, открытые вклады и их суммы,
проведённые операции и обороты, закрытия операционного дня. Итоги считает
`StaffWorkCalculator` (домен, покрыт тестами).

### 6.5. Личный кабинет клиента

Вход по номеру документа и дате рождения (дата фиксируется при первом входе).
Кабинет только читает данные: вклады, сроки, начисления, ожидаемый доход,
оценку досрочного возврата и опубликованные условия вкладов банка.

## 7. Обработка ошибок и журналирование

Исключения прикладного слоя (`AppException`, `NotFoundException`,
`ConflictException`, `ForbiddenException`) преобразуются middleware в
ProblemDetails с кодом HTTP. Все значимые действия (вход, регистрация клиента,
открытие счёта, операция, сторно, закрытие дня, изменение пользователей)
записываются в `AuditLog` без возможности изменения задним числом.
